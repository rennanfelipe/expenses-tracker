# Go Coding Standards

## 1. General Principles

The project must follow idiomatic Go practices and prioritize simplicity, readability, maintainability, and reliability.

The coding agent MUST follow these principles:

1. Prefer simple and explicit implementations over clever abstractions.
2. Follow established Go conventions and standard library practices.
3. Avoid unnecessary dependencies.
4. Avoid premature optimization.
5. Write code that is easy to understand, test, and maintain.
6. Keep responsibilities separated without introducing unnecessary architectural complexity.
7. Prefer composition over inheritance-like abstractions.
8. Do not introduce abstractions without a concrete use case.
9. Do not duplicate business rules across different interfaces.
10. Preserve existing architectural decisions unless explicitly instructed otherwise.

The agent MUST NOT introduce new architectural patterns, frameworks, or dependencies without explaining their necessity and obtaining approval.

## 2. Go Version and Tooling

- Use the Go version specified in `go.mod`.
- Do not upgrade the Go version without authorization.
- Use Go modules for dependency management.
- Prefer the Go standard library whenever it provides a suitable solution.
- Use `gofmt` to format all Go source files.
- Use `go vet` to identify suspicious constructs.
- Ensure `go test ./...` passes before considering a task complete.

Recommended tooling:

```bash
gofmt -w .
go vet ./...
go test ./...
go test -race ./...
```

The race detector should be used when relevant, particularly when introducing concurrency.

## 3. Project Structure and Packages

Follow Go's package-oriented design.

Guidelines:

1. Packages MUST have a clear and cohesive responsibility.
2. Avoid packages that contain unrelated functionality.
3. Avoid creating packages solely to group files.
4. Keep implementation details private whenever possible.
5. Export only identifiers that need to be accessed outside their package.
6. Avoid circular dependencies.
7. Avoid excessively deep directory structures.
8. Do not create a `utils`, `helpers`, or `common` package containing unrelated functions.

Use `internal/` for application implementation details that should not be imported by external projects.

Use `cmd/` for application entry points when the project requires multiple executables.

Do not introduce `pkg/` automatically. Public packages should exist only when there is a concrete requirement for external reuse.

## 4. Naming Conventions

Follow standard Go naming conventions.

### Packages

- Use short, lowercase names.
- Avoid underscores and mixed capitalization.
- Prefer singular package names.
- Avoid generic names such as `common`, `base`, or `utils`.

### Variables and Functions

- Use `camelCase` for unexported identifiers.
- Use `PascalCase` for exported identifiers.
- Prefer descriptive names over abbreviations.
- Use established Go abbreviations such as `ID`, `URL`, `HTTP`, and `CSV`.
- Keep names concise without sacrificing clarity.

Examples:

```go
var transactionID string
var createdAt time.Time

func CreateTransaction() {}
func ParseCSVStatement() {}
```

Avoid meaningless names:

```go
var data interface{}
var result interface{}
var temp string
```

Short variable names such as `i`, `err`, `ctx`, and `r` are acceptable within limited scopes.

### Interfaces

- Name interfaces according to their behavior.
- Prefer names ending in `-er` when appropriate.
- Keep interfaces small.

Examples:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type TransactionRepository interface {
    Save(ctx context.Context, tx Transaction) error
}
```

Do not create interfaces for every struct automatically.

## 5. Formatting and Code Style

- Follow `gofmt` formatting without exceptions.
- Use tabs for indentation as generated by `gofmt`.
- Keep functions focused on a single responsibility.
- Avoid deeply nested conditionals.
- Prefer early returns to reduce nesting.
- Avoid unnecessarily long functions.
- Group related declarations logically.
- Remove unused variables, imports, and functions.

Prefer:

```go
func ImportStatement(ctx context.Context, file string) error {
    if file == "" {
        return errors.New("statement file cannot be empty")
    }

    // Implementation
    return nil
}
```

Avoid unnecessary nesting:

```go
func ImportStatement(ctx context.Context, file string) error {
    if file != "" {
        if valid(file) {
            if accessible(file) {
                // Implementation
            }
        }
    }

    return nil
}
```

## 6. Error Handling

Error handling MUST be explicit.

1. Never silently ignore errors.
2. Never use empty error handling blocks.
3. Return errors to callers when they cannot be handled locally.
4. Handle errors at the appropriate application boundary.
5. Add contextual information when propagating errors.
6. Use `errors.Is` and `errors.As` when inspecting wrapped errors.
7. Use sentinel errors only when callers need to identify specific conditions.
8. Avoid panic for normal application error conditions.

Wrap errors using `%w`:

```go
if err != nil {
    return fmt.Errorf("import transaction statement: %w", err)
}
```

Define sentinel errors when appropriate:

```go
var ErrDuplicateTransaction = errors.New("duplicate transaction")
```

Do not expose database-specific errors directly through presentation interfaces.

Never discard errors from operations involving financial data persistence.

## 7. Functions and Methods

- Functions SHOULD perform one clearly defined operation.
- Prefer explicit parameters over hidden dependencies.
- Avoid excessive numbers of parameters.
- Use structs when a group of parameters represents a meaningful concept.
- Avoid unnecessary receiver methods.
- Use pointer receivers when mutation or avoiding copies of large structures is appropriate.
- Use value receivers for small immutable values when appropriate.
- Avoid methods that mutate their receiver unexpectedly.

Avoid unnecessary global state.

Dependencies SHOULD be passed explicitly through constructors or function parameters.

## 8. Structs and Data Modeling

- Use structs to represent domain concepts.
- Keep domain structures independent of database and presentation concerns.
- Avoid mixing persistence-specific fields with business behavior.
- Use appropriate Go types instead of representing everything as strings.
- Use `time.Time` for dates and timestamps where appropriate.
- Use explicit types for domain concepts when they improve correctness.

Financial amounts MUST NOT use `float32` or `float64`.

Use integer-based monetary representation (for example, integer cents) or an explicitly selected decimal representation.

Example:

```go
type Money struct {
    Cents int64
    Currency string
}
```

Ensure monetary calculations preserve precision.

Do not use floating-point arithmetic for financial calculations.

## 9. Context and Cancellation

Use `context.Context` for operations that require cancellation, deadlines, or request-scoped values.

Guidelines:

1. Pass context explicitly as the first parameter.
2. Never store context in structs.
3. Never pass nil contexts.
4. Propagate context through database and external I/O operations.
5. Respect cancellation signals in long-running operations.
6. Do not use context as a general-purpose parameter container.

Example:

```go
func ImportStatement(ctx context.Context, path string) error {
    // Processing implementation
    return nil
}
```

## 10. Concurrency

Concurrency MUST be introduced only when there is a demonstrated need.

- Prefer sequential processing when it is sufficient.
- Avoid unnecessary goroutines.
- Always establish clear ownership of shared resources.
- Protect shared mutable state appropriately.
- Use channels when they simplify communication and ownership.
- Avoid channel usage when ordinary function calls are simpler.
- Ensure goroutines have a clear termination mechanism.
- Handle cancellation and errors in concurrent operations.

Do not introduce concurrency into CSV processing or report generation merely for performance assumptions.

## 11. Interfaces and Abstraction

Follow Go's implicit interface implementation model.

1. Define interfaces close to where they are consumed.
2. Prefer small interfaces.
3. Avoid interfaces containing methods that are not required by their consumers.
4. Do not create interfaces for every concrete implementation.
5. Use dependency injection when it improves testability or decoupling.
6. Avoid unnecessary abstraction layers.

For example, a consumer that only needs to retrieve transactions should not depend on an interface containing every database operation.

Do not introduce generic programming unless it solves a concrete problem more clearly than ordinary Go code.

## 12. Database and Persistence

Database access MUST remain separated from domain logic.

- Use parameterized SQL queries.
- Never concatenate user input into SQL statements.
- Handle database errors explicitly.
- Use transactions for operations requiring atomicity.
- Define appropriate database constraints.
- Avoid N+1 query patterns.
- Use context-aware database operations.
- Close rows and other database resources appropriately.
- Check `rows.Err()` after iterating over SQL rows.
- Use migrations for schema changes.
- Never modify production database schemas implicitly.

Database-specific implementations MUST NOT leak into domain entities.

Financial data MUST preserve its original precision and relevant source information.

## 13. CSV and ETL Processing

CSV processing is a core responsibility of Expenses Tracker.

The implementation MUST follow these guidelines:

1. Separate CSV extraction, transformation, validation, and persistence.
2. Do not couple CSV parsing directly to database operations.
3. Treat each bank's CSV format as a distinct input format.
4. Validate required columns and supported formats.
5. Handle malformed records explicitly.
6. Never assume a particular column order unless guaranteed by the format.
7. Normalize dates explicitly.
8. Normalize monetary values without losing precision.
9. Preserve transaction information required for auditing and troubleshooting.
10. Handle duplicate detection according to established business rules.
11. Report import failures clearly.
12. Avoid silently discarding invalid records.

CSV parsing MUST NOT contain business categorization rules directly.

Bank-specific parsing logic SHOULD be isolated from the domain model.

The ETL process SHOULD support deterministic transformations: identical valid input and configuration should produce identical normalized output.

Do not assume that every bank uses the same date, decimal, transaction description, or amount conventions.

## 14. Testing

All significant business logic MUST have automated tests.

Use the standard Go testing package unless another testing library is explicitly justified.

### Unit Tests

- Test functions and methods independently.
- Test expected results.
- Test invalid inputs.
- Test boundary conditions.
- Test error handling.
- Avoid depending on external services.

### Integration Tests

Use integration tests when verifying interactions with:

- Databases.
- Filesystems.
- CSV import pipelines.
- External services.

### Table-Driven Tests

Prefer table-driven tests when testing multiple input/output combinations.

Example:

```go
func TestParseAmount(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    int64
        wantErr bool
    }{
        {
            name:  "valid amount",
            input: "125,50",
            want:  12550,
        },
        {
            name:    "invalid amount",
            input:   "invalid",
            wantErr: true,
        },
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := ParseAmount(tt.input)

            if (err != nil) != tt.wantErr {
                t.Fatalf("ParseAmount() error = %v, wantErr %v", err, tt.wantErr)
            }

            if err == nil && got != tt.want {
                t.Errorf("ParseAmount() = %d, want %d", got, tt.want)
            }
        })
    }
}
```

Tests MUST be deterministic and MUST NOT depend on execution order.

Never modify tests merely to make an incorrect implementation pass.

## 15. Documentation

- Document all exported identifiers using Go documentation conventions.
- Document non-obvious business logic.
- Explain why a complex implementation exists rather than describing obvious code.
- Keep README documentation updated when application behavior changes.
- Document environment variables and configuration options.
- Include examples for non-obvious public APIs.

Avoid excessive comments that duplicate the implementation.

## 16. Security

- Never hardcode credentials, passwords, API keys, or secrets.
- Use environment variables or an appropriate secrets management mechanism.
- Validate external input.
- Avoid exposing sensitive financial information in logs.
- Do not log complete credit card statements.
- Avoid logging authentication credentials or database connection strings.
- Use secure database connection configurations where applicable.
- Do not expose internal errors or stack traces to end users.
- Follow the principle of least privilege.

## 17. Logging

Use Go's standard `log/slog` package unless the project has an established alternative.

Guidelines:

- Prefer structured logging.
- Use appropriate log levels.
- Include contextual information.
- Avoid logging sensitive financial data.
- Never use logging as a replacement for error handling.
- Do not introduce excessive logging in normal application paths.

## 18. Dependencies

- Prefer the standard library.
- Evaluate maintenance status before introducing dependencies.
- Avoid dependencies that duplicate existing functionality.
- Do not introduce a framework solely for convenience.
- Keep dependencies updated according to project maintenance policies.
- Review dependency licenses and security implications.
- Do not modify `go.mod` or `go.sum` unnecessarily.

Before introducing a new dependency, explain:

1. What problem it solves.
2. Why the standard library is insufficient.
3. Whether an existing dependency already provides the functionality.
4. Its maintenance and security considerations.

## 19. Code Review and Change Management

Before completing any implementation task, the coding agent MUST:

1. Review the existing project structure.
2. Understand the relevant architecture and existing conventions.
3. Avoid modifying unrelated files.
4. Implement only the requested scope.
5. Run relevant automated tests.
6. Run `go vet ./...` when applicable.
7. Review the final diff.
8. Identify any limitations or unimplemented requirements.
9. Report all files created, modified, or deleted.

The agent MUST NOT:

- Silently change public interfaces.
- Remove existing functionality without authorization.
- Introduce unrelated refactoring.
- Ignore failing tests.
- Claim successful execution of commands that were not actually executed.
- Modify requirements or architecture documents to justify an implementation that violates them.

## 20. Definition of Done

An implementation task is considered complete only when:

- The implementation satisfies the requested requirements.
- The code follows these coding standards.
- The code is formatted with `gofmt`.
- Relevant tests pass.
- No known compilation errors remain.
- Error handling is implemented appropriately.
- No credentials or sensitive information have been introduced.
- Documentation is updated when necessary.
- The final changes have been reviewed.

If a requirement cannot be implemented without changing an established architectural decision, the agent MUST stop and explain the conflict before proceeding.
