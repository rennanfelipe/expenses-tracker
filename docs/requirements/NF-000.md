# Expenses Model — Requirements

## 1. Objective

Implement a Model component responsible for performing CRUD (Create, Read, Update, Delete) operations on the `expenses` table defined in `db-schemas/db.sql`.

The component must provide the functionality required to create, retrieve, update, and delete expense records using MariaDB.

## 2. Mandatory prerequisite: inspect the database schema

**Before implementing anything, the agent MUST read `db-schemas/db.sql`.**

The SQL file is the authoritative source for the database structure.

The agent must identify and understand:

- The columns defined in the `expenses` table.
- Column names and data types.
- Primary keys and auto-increment behavior.
- Nullable and non-nullable columns.
- Default values.
- Unique constraints.
- Foreign keys and relationships, if any.
- Indexes and other relevant constraints.

Implementation must match the actual schema.

Do not:
- Assume column names or data types.
- Introduce fields that are not defined in the SQL schema.
- Change the database schema to accommodate the implementation.
- Ignore constraints or defaults defined in the SQL file.

If the schema does not provide enough information to implement a requirement safely, report the ambiguity instead of inventing behavior.

## 3. Architecture requirements

Follow the project's MVC architecture and the instructions in:

- `AGENTS.md`
- `ai/architecture-rules.md`
- `ai/coding-standards.md`
- `ai/testing-guidelines.md`

The implementation belongs in the Model.

The Model is responsible for:
- Database access and SQL execution.
- Mapping database records to Go structures.
- Validating data according to applicable business rules.
- Handling database errors.
- Providing CRUD functionality.

Do not introduce an Infrastructure layer, Domain layer, Application layer, or unnecessary abstractions.

Keep the implementation cohesive within the Model. Follow the existing project structure and naming conventions.

## 4. Functional requirements

Implement the following operations.

### 4.1 Create expense

Provide an operation to insert a new expense record.

Requirements:
- Accept the fields required by the `expenses` table.
- Let MariaDB handle auto-generated values and defaults where applicable.
- Return the created record or its generated identifier.
- Handle constraint violations and database errors.
- Do not accept or overwrite database-managed values unnecessarily.

### 4.2 Retrieve expenses

Provide operations to:

- Retrieve a single expense by its primary key.
- Retrieve all expenses.

Requirements:
- Return records mapped to the appropriate Go structure.
- Handle cases where a requested record does not exist.
- Properly close database result sets.
- Propagate database errors.

### 4.3 Update expense

Provide an operation to update an existing expense.

Requirements:
- Identify the record using its primary key.
- Update only the fields supported by the database schema.
- Prevent accidental modification of database-managed fields.
- Handle cases where the record does not exist.
- Handle database constraint violations and other errors.

### 4.4 Delete expense

Provide an operation to delete an expense using its primary key.

Requirements:
- Execute the deletion against the correct record.
- Handle cases where the record does not exist.
- Propagate database errors.
- Respect foreign key constraints, if defined.

## 5. Database requirements

- Use the existing MariaDB connection configuration and project conventions.
- Use parameterized SQL queries.
- Never concatenate user-provided values into SQL statements.
- Use `context.Context` for database operations.
- Handle database errors explicitly.
- Avoid unnecessary database queries.
- Do not introduce another database engine or ORM unless explicitly authorized.

## 6. Data handling

- Go structures must accurately represent the columns in `db-schemas/db.sql`.
- Use appropriate Go types for the corresponding SQL data types.
- Handle nullable columns correctly.
- Preserve the precision of monetary values. Do not use `float32` or `float64` for financial calculations or storage.
- Handle dates and timestamps according to their actual SQL definitions.

## 7. Testing requirements

The implementation must be testable and follow `ai/testing-guidelines.md`.

The Tester Agent is responsible for developing and maintaining the tests.

The following scenarios must be covered:

- Successful expense creation.
- Creation with invalid or missing required data.
- Successful retrieval by ID.
- Retrieval of a nonexistent ID.
- Successful retrieval of all expenses.
- Successful expense update.
- Update of a nonexistent expense.
- Successful expense deletion.
- Deletion of a nonexistent expense.
- Database constraint violations.
- Database connection or query failures.

Use MariaDB integration tests where database behavior needs to be verified. Do not substitute SQLite for MariaDB integration tests.

## 8. Scope restrictions

This requirement covers CRUD operations for the `expenses` table only.

Do not implement:
- Expense reporting or aggregation.
- CSV import or export.
- Category management.
- Authentication or authorization.
- CLI, TUI, or Web presentation.
- Additional database tables or schema migrations.
- Features unrelated to expense CRUD.

Do not modify `db-schemas/db.sql` unless explicitly requested.

## 9. Completion criteria

The implementation is complete when:

- The agent has inspected `db-schemas/db.sql`.
- The implementation matches the actual database schema.
- All four CRUD operations are implemented.
- Database errors are handled appropriately.
- The implementation follows the project's MVC architecture.
- Existing project tests continue to pass.
- The Tester Agent has been informed of the implementation and the test scenarios that require coverage.
